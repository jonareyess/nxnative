# Trails in the Sky 1st Chapter (`01002C9022770000`)

Updates 1.0.4 (v196608) and 1.0.7 (v393216), SDK 19.3.13, Falcom's engine on NVN. Modules `main`, `subsdk0` and `sdk`. The profile was recovered from a 1.0.4 Mac app with about 25 hours of owner-reported gameplay. The previous 1.0.7 app was validated on M1 for furniture, menu eyes, bestiary models, reflections and DLC. The November 13 integration built all 6,602 shaders and loaded that save; the GPU-memory correction has an initial owner walking/combat playtest without memory errors, menu eyes and bestiary lighting are also revalidated, while frame-time drops and reflection revalidation remain open. iOS is untested.

## Integration on current main

The remaining changes are the game profile, invocation-private compute storage, and a synthetic GLSLC gap test. Memory-pool handling is upstream (`34856df4`). Pipeline-selected integer outputs, image-type fitting, GLSLC section offsets and M1/M2 thread limits all use main's implementations. No host or offline-archive alternative is retained.

Current validation (M1, macOS 27.2.1, Xcode 27.2, 2026-11-14): `regress.py check --games 01002C9022770000` against `1df3182f88c0`, 70 seconds per side, reports CHANGED with no new failure. Both build 6,602/6,602 shaders; only `43c2b838b11bc19c` and `adc43567131a8e59` change MSL, with one reflection change as private storage removes the spill. Both load the same indoor save, reach frames 3,535 / 3,562 and stop at the harness deadline without a crash, hang or red line. Settled fps is 59.5 / 59.6 and frame p99 17.69 / 17.06 ms: one run per side, not evidence of a speedup. The 55- and 65-second screenshots show the same room; idle animation and rotating tip text account for their visible differences. Menu eyes, bestiary lighting, reflections and longer combat are not revalidated by this indoor route; the November 13 playtests below remain historical evidence.

[`smoke.tsv`](smoke.tsv) uses a fixed copy of the indoor save at `<NSP folder>/smoke-save`. It presses A to load Continue and leaves the character in place. The harness copies that save for each run and keeps cloud sync off. Trails is the only available local Mac build; the other games reached by a general compute rewrite remain unchecked in this revision.

## What it needs

| Setting | Why |
|---|---|
| `mem_reserve 0x1100000000`, `mem_alias 0x1000000000` | The engine reserves a virtual address region about ten times its allocator size on the Mac. The observed physical heap is 2.02 GB; the 64 GB alias range is virtual. The smaller provisional layout failed its heap check. |
| `sys_resource 0x1000000` | The NPDM declares 16 MB of system resource. |
| `depth_mode zero` | At boot the game sets near depth to zero; prebuilt vertex pipelines must use `main0_z`. |
| `shader_groups` | Shader files are under `asset/nx/shader`; the other groups keep the split's package paths stable. |

The registered build IDs in [`game.tsv`](game.tsv) cover both updates. The default package and shader tables are from 1.0.7. The base game has not been tested.

## Mac observations

- **November 13 integration validated by the owner on M1 (2026-11-13): menu eyes and bestiary lighting.** The owner rechecked both with the current-main integration and confirms they are correct. This validates using main's [pipeline-selected integer outputs](../../../docs/reference/shaders.md#integer-outputs-told-by-the-pipelines-targets) in place of this PR's historical mixed-output alternatives. Reflection revalidation and longer-session stability remain open.

- **Resolved: update 1.0.7 missing scene objects on M1 (2026-11-02).** Shader `43c2b838b11bc19c` initially failed pipeline creation because of its 44 KB shared allocation. The general [invocation-private shared array lowering](../../../docs/reference/shaders.md#invocation-private-shared-arrays-exceed-metals-threadgroup-limit) reproduces the working 1.0.4 correction exactly. That alone eliminates the error but leaves furniture absent. That historical build also needed a second local change listed in the old app's metadata: [fixed group sizes guide register allocation](../../../docs/reference/shaders.md#compute-dispatches-past-the-pipelines-thread-limit). The shader's default Metal pipeline supports only 768 threads; it supports its required 1,024 with the explicit descriptor. The owner confirms that furniture rendered again with both historical changes. Current main supplies the fixed size in the kernel's `max_total_threads_per_threadgroup` attribute, so this profile no longer adds a host or offline-archive descriptor override. Its generic shared-memory spill also handles the 44 KB allocation; private lowering avoids that spill for disjoint per-invocation storage. The material-output fix below also resolves the model colours.
- The older 1.0.4 log records a session through frame 669,900, with save transactions still completing. In the last 300-frame interval, frame time was p50 16.66 ms and p95 16.83 ms, GPU p95 7.24 ms and the reported footprint 3,057 MiB on an Apple M1. These numbers describe that interval, not every scene.
- It logs two calls to unimplemented NVN functions: `nvnCommandBufferSetZCullZF32CompressionEnable` near boot and `nvnCommandBufferSetControlMemoryCallbackEnabled` later. No corresponding crash appears in the session log. Their effects are not established.
- **Resolved: incorrect iris colours (owner validation).** Reproduced in both 1.0.4 and the rebuilt 1.0.7, in Costume using a copy of the 25-hour save: Joshua's model has a red-looking iris beside an amber one, while his portrait shows yellow irises. There are two `chr_eye` draws: vertex `cfc9057b69fa8e4e` / pixel `b503751171dcdeff` draws the opaque iris; vertex `e001d2cbd46e29f5` / pixel `f2e6f8b3abe2214f` adds the blended highlight later. The 512×512 BC7 colour texture and its first seven mip levels decode to the expected amber iris; the two eyes' corresponding mesh UVs match. Merely changing the highlight shader's colour does not remove the asymmetry. Offline frame replay isolates the tint to SSAO combine pixel shader `a58cf7e9ad7ff74a`. The opaque iris writes packed material bits `0x7bde` as a constant to integer MRT 3; the generated mixed entry incorrectly has mask 6 rather than 14. Correcting that output type restores both gold irises in the captured frame. The historical correction, now superseded by [pipeline-selected integer outputs](../../../docs/reference/shaders.md#integer-outputs-told-by-the-pipelines-targets) was built into the Mac app (chain `41af1cd4e607`). The owner confirms that both the menu-model eyes and bestiary models render correctly with this app.

- **Improved in owner playtesting: periodic microstutter.** After furniture was restored, visuals and monster detail improved, but the owner observed brief drops from 60 to about 55 fps every few seconds and reported 100% GPU utilization. After the cube image-store correction below, the owner reports that the periodic FPS jumps also seem to have disappeared. No same-scene timing comparison establishes the size or cause of that improvement; GPU saturation as the earlier explanation remains an owner observation.

- **Resolved: intermittent glass and metal reflection artifacts (owner validation).** The owner first reported incorrect reflections on building windows and a character's glasses in 1.0.7, absent in the older 1.0.4 app. An initial playtest after the material-output correction did not reproduce them, but later playtesting of that app (chain `41af1cd4e607`) reproduced an oily appearance on metal too: Estelle's blue shoulder armour, Joshua's shoulder armour and bracers, and a metal plaque behind them. The diffuse clothing and faces appeared unaffected. The cause is separate from the iris material-output correction: [cube image stores need face-array views](../../../docs/reference/rendering.md#image-views-of-the-type-a-shader-declares). The owner confirms that the same glass and armour render correctly after the host correction, using the existing shaders.
  - Frame 15,444 captures the defect outside Lavantar Casino & Bar, on the windows and the characters' armour. The capture is complete (no omitted textures or addresses outside its pools; SHA-256 `8a1eade9f6b0b94ec2b03c914123b0d90205c1fe4aceaf24e55d25b86a814bb1`). Three fresh diagnostic replays produce the same image, differing from the live capture in 109 pixels with a maximum per-channel difference of 5. The affected passes share environment texture serial 4,638,785 (512×512 RGBA8, six faces, ten mip levels; deferred shader `567fcd0c97a29418`, texture slot 145). Its captured Metal texels and its deswizzled pool storage match exactly in all 60 face/level pairs and already contain the coloured pattern. Zeroing only that captured texture in an offline diagnostic removes the artifacts from both glass and armour; this disables the reflection contribution and is not the fix. Neither cube producer runs in this captured frame.
  - A subsequent trace from boot reproduces the defect outside Hotel Blanche. At frame 885, `cubemap_copy` (`770559397e473ebb`) writes serial 87,182, then `cubemap_blend` (`ea9d6c8d8dd336d3`) writes serial 87,171, using cube views for each of the ten mip levels. Sampled aliases 87,181 and 87,170 share their respective backing, so an allocation mismatch does not explain this run. Both compute shaders declare float `texture2d_array` outputs. The host bound cube views to those outputs; converting the image bindings to face-array views restores their writes. The owner confirms the correction on the same affected materials in the rebuilt host.

## Found on this game

- [Unknown-length lookups made a chunk at every stride](../../../docs/reference/memory.md#unknown-length-lookups-made-a-chunk-at-every-stride): the correction is integrated upstream as `34856df4`; this PR no longer changes pool lookups or their tests.

- [Image views of the type a shader declares](../../../docs/reference/rendering.md#image-views-of-the-type-a-shader-declares): environment updates must write through array views of their cube descriptors.
- [Integer outputs told by the pipeline targets](../../../docs/reference/shaders.md#integer-outputs-told-by-the-pipelines-targets): the current integration uses main's per-target integer specialization; the older mixed-output alternatives are no longer part of this profile.

- [Invocation-private shared arrays exceed Metal's threadgroup limit](../../../docs/reference/shaders.md#invocation-private-shared-arrays-exceed-metals-threadgroup-limit): the scene-object compute shader needs only 11 private words per invocation.
- [Compute dispatches past the pipeline's thread limit](../../../docs/reference/shaders.md#compute-dispatches-past-the-pipelines-thread-limit): its historical 1,024-thread shader compiled for at most 768 threads on M1; main's kernel attribute now replaces the descriptor override.
- [GLSLC outputs read through their section headers](../../../docs/reference/shaders.md#glslc-outputs-read-through-their-section-headers): upstream's section-first reader recovers one shader from `main`; this PR retains a synthetic gap regression, not another reader rule.
- [Branches within an exclusive window](../../../docs/reference/rewriter.md#branches-within-an-exclusive-window): update 1.0.7's `main` has an internal branch to its store-exclusive and an unconditional branch past it; both must be copied with the window.

## Open

- **Open: owner playtest improves with acquire-only real-time policy (2026-11-13).** The same corrected app was launched with `DM_RT_FRAME=0`, a copied initial save, isolated save/cache folders and the performance HUD. The boot log confirms that only the acquire thread declared a time-constraint policy. The owner reports substantially fewer severe drops. The run reaches timing frame 10,500, exits 0 and has no `[RED]` lines. After frame 3,000, the median of the 26 reported 300-frame window medians is 16.79 ms, and the median of their p95s is 25.60 ms; no window has frame-time p50 at least 30 ms. The previous session's 53 post-load windows give 18.57 ms and 35.91 ms respectively, with nine windows at or above 30 ms. Maximum periodic Metal allocation is 3,091 MB. The sessions differ in duration and the route is manual; these are descriptive window statistics, not global frame percentiles or a deterministic benchmark. The comparison implicates frame-thread real-time declarations but does not establish the scheduling failure or justify disabling them globally. The switch is limited to the test launcher; no default or profile change is included in the PR. Evidence: `playtest-rtframe0-20261113-200229/` in the NSP folder.

- **Owner validation: corrected build survives walking and combat; performance remains open (2026-11-13).** The `memoryfix 20261113` app (`822db90331c2`, chain `3363652a27da`; same production code as this integration) ran for about 436 seconds of frame-loop time and exited normally. No `[RED]` line or GPU out-of-memory error appears. Periodic Metal allocation stabilized from 3,137 MB at frame 6,900 to 3,153 MB at frame 15,900; maximum periodic resident memory was 3,007 MB. The owner's approximate HUD reading was 3.5 GB, which may include unsampled peaks. Walking and combat both had drops to about 30 fps. At frame 8,700 the 300-frame window had frame-time p50 30.55 ms / p95 47.47 ms, while GPU p50 was 19.11 ms / p95 21.64 ms. Some individual frames took 90–170 ms despite roughly 18–26 ms of GPU time and no new pipeline or shader-library compilation; these counters do not identify the remaining host/game scheduling or presentation delay. The log is preserved under the NSP folder's `01002C9022770000-work/memoryfix-owner-20261113/`. This validates this walking/combat session against the previous memory failure, not long-session stability or restored old-build performance. A same-scene timing and GPU-pass comparison is still needed before changing performance policy.

- **Resolved upstream: unbounded GPU buffer extents (`34856df4`, 2026-11-14).** The [general pool lookup correction](../../../docs/reference/memory.md#unknown-length-lookups-made-a-chunk-at-every-stride) replaces the 64 MB guesses with a single whole-pool view when the GPU access has no known bound. A 70-second scripted load of the initial save reached frame 3,900 with 2,685 MB allocated by Metal and no GPU-memory error; the first loaded-scene sample at frame 900 and the final changed-memory sample at frame 3,900 both report 2,685 MB. The screenshot at frame 2,400 shows the loaded indoor scene. This is a boot/indoor check, not a repeat of the owner's broad-area combat route; this scripted check alone does not establish long-session stability; subsequent owner gameplay and visual validation are recorded separately. The corrected host's synthetic pool tests pass 171 checks, including a GPU access 96 MB past an unbounded address; the same fixture against the pre-fix renderer fails 20 checks and safely skips that out-of-range GPU probe. The two-game static regression against `b06f4e0e` is CHANGED for this game (6,602/6,602, no new shader or interface failures, two expected MSL changes from private scratch) and PASS for Red Dead Redemption (3,628/3,628, no MSL changes); neither profile had a smoke route, so that report supplies no runtime comparison.

- **Historical regression: GPU memory exhaustion on M1 (2026-11-13), resolved upstream in `34856df4`.** Owner playtest of 1.0.7, host based on `b06f4e0e`, chain `3363652a27da`, using a local copy of the iCloud save. Metal allocation rose from 1,946 MB at frame 1,200 to 4,590 MB at frame 1,500 and 5,212 MB at frame 10,500. The first failed submission was frame 10,377, after about 189 seconds of frame-loop time: `kIOGPUCommandBufferCallbackErrorOutOfMemory`. The first residency census reported 5,458 MB against Metal's recommended 5,461 MB: 119 shared buffers / 4,243 MB, 754 textures / 1,023 MB, six private buffers / 192 MB. Many shared buffers were 100 MB. The owner reports worsening performance and roughly 5.5 GB in the HUD, versus roughly 2.8 GB (corrected owner reading) and stable play in the installed older app (`65c72138a9fb+dirty`, chain `f63db5f967ac`); those are not same-route A/B measurements. A subsequent instrumented run identified unbounded indirect-index lookups creating overlapping guessed spans; see the [general correction](../../../docs/reference/memory.md#unknown-length-lookups-made-a-chunk-at-every-stride). Superseded views remain alive deliberately for already encoded GPU addresses. The captured run ends with host exit 0 after repeated GPU failures; no fatal signal is recorded. Logs and memory samples are preserved in the NSP folder's `playtest-20261113-182105/`.
  - **Older-build comparison:** the owner repeated approximately the same route from the identical initial save using the installed older app. `playtest-old-20261113-183310/game.log` reaches frame 31,500, ends with host exit 0 and contains no GPU out-of-memory or recorded fatal signal. Periodic Metal allocation reaches at most 2,734 MB and resident memory at most 2,656 MB; the final 300-frame window has frame time p50 16.99 ms / p95 21.76 ms. The owner reports mostly 60 fps, dips to about 45, and no progressive loss of playability. The new build reaches 5,212 MB Metal allocation and GPU failures before frame 10,500; its frame-13,200 window is p50 37.50 ms / p95 43.67 ms. Both runs have seven guest memory pools; the old run reports six resident pool entries, the new up to 49 (large-pool chunks can produce multiple entries). The route was manually repeated, not a deterministic benchmark; the later corrected owner walking/combat session is recorded above.
